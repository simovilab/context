## Directives (composed)

### code.open-source

Software must be released open-source under a permissive license.


_from: project_

### code.review-and-commits

Changes must land via reviewed pull requests. Use Conventional Commits (feat, fix, docs, chore, refactor, test, perf, ci) for all commit messages.


_from: project_

### data.fair-mdip

Published data must be Findable, Accessible, Interoperable, and Reusable (FAIR), and must align with the Mobility Data Interoperability Principles (MDIP).


_from: project_

### data.gtfs-standard

GTFS is the canonical exchange format for this system: GTFS Schedule for static data and GTFS Realtime Alerts for operational alerts.


_from: project_

### data.no-pii

Never collect, store, or publish personally identifiable information (PII). No PII is required for this system, and this is a hard commitment, not a target.


_from: project_

### data.open-license

Published GTFS data must use an open, permissive license (recommended: Creative Commons Attribution 3.0 / CC BY 3.0). Published data is open and public domain, with no access or use restrictions.


_from: project_

### docs.language-policy

Write technical and agent-facing documentation in English; use Spanish for institution-facing content such as public materials and deliverable names. Never mix languages within a single file (D7).


_from: project_

### security.audit-logging

Handling of public-transport data must produce activity logs sufficient for traceability, audit, and anomaly detection (CS6).


_from: project_

### security.authn-authz

Authentication and authorization must use mechanisms with token expiration and controlled renewal, for both human users and system-to-system access (CS5).


_from: project_

### security.database-hardening

Databases must sit behind authentication with strong credential and password policies, and must have periodic backup policies to prevent data loss (CS3).


_from: project_

### security.hosting

During the development period, the system must be hosted on University of Costa Rica (UCR) servers, which provide high-level security and 24/7 attack response (CS1).


_from: project_

### security.input-validation

All inputs on web interfaces must be validated to prevent SQL injection, XSS, and CSRF attacks (CS8).


_from: project_

### security.monitoring

Performance and security must be monitored with specialized software providing 24/7 alerting for cyberattacks and operational faults (CS7).


_from: project_

### security.no-sensitive-in-source

Source code must never contain personal, institutional, or business-sensitive data; never commit secrets, credentials, or internal URLs (CS2).


_from: project_

### security.transport-encryption

All traffic to and from the system must be encrypted in transit via HTTPS/TLS or an equivalent protocol (CS4).
