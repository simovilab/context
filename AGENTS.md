# AGENTS.md

## What this repo is

**InfoTP Context Studio** is a git-first, self-hosted context store for the national InfoTP public-transport project (SIMOVI / EIE-UCR / Fundación UCR). It is **not runnable code** — it is versioned context, served to AI coding agents and humans. Context is modeled as cascading configuration, Project → Component → Deliverable, the same way CSS specificity or layered config files cascade: each layer can set, extend, or suppress what came before it.

## Directive vs. reference context

There are two kinds of context, and they compose differently:

- **Directive context** — rules and instructions (commit conventions, coding standards, security posture, governance). Composition is by specificity: the most-specific node wins per key. Directives get inlined into an agent's context window, so they are **token-budgeted** — filtered by node `kind` so irrelevant rules (and their tokens) never load.
- **Reference context** — knowledge and documents (specs, diagnostics, corpora). It **accumulates**: a node's reference context is the union of its own plus everything above it in the tree. It is fetched on demand via RAG, so it costs ~0 always-on tokens.

## Where things live

| Layer | Location |
|---|---|
| Project (cross-cutting) | `project/` (`node.yaml`, `directives.yaml`, `brief.md`) |
| Components | `components/C#/` (`node.yaml`, `directives.yaml`, `charter.md`) |
| Deliverables | `components/C#/deliverables/C#P#/` (`node.yaml`, `reference.md`, `corpus/`) |
| Reference corpus | `<node>/corpus/` — source documents + `manifest.yaml` (the manifest is the source of truth for what a node contributes to RAG) |
| Generated/composed context | `.composed/` (`<ID>.json`, `<ID>.md`) — CI-built, never hand-edited |
| RAG index | `.rag/` — derived, **gitignored** build artifact; rebuilt on demand, never committed |
| Schemas | `schemas/` (`node.schema.json`, `directives.schema.json`, `corpus.schema.json`) |
| Build tooling | `tools/composer/` (Python composition engine), `tools/rag/` (Python branch-scoped RAG engine), and `tools/studio/` (local authoring UI) — not context |

## How composition works

For any node, composition walks from `project/` down to that node, collecting directives from every ancestor plus the node itself; for each directive `key`, the most-specific node's `op` wins (`set` replaces, `extend` appends, `suppress` removes it going forward), and only directives whose `applies_to` intersects the node's `kind` survive. Reference context is simpler: every ancestor's reference material is unioned into the node's available corpus, with nothing filtered out. The result of this walk is regenerated by CI into `.composed/<ID>.json` (for MCP) and `.composed/<ID>.md` (for humans) — these files are generated output and must never be hand-edited.

## Conventions

- Filenames: kebab-case.
- Every layer is a node folder with a `node.yaml` (structured identity) + `directives.yaml` (rules) + a prose file — `reference.md` at deliverables, `charter.md` at components, `brief.md` at the project root (D2). A node's `kind` selects which directives apply; a component's `kind` is the union of its deliverables'.
- Node IDs are the proposal's own codes (C#P#, INF#); dependency edges are stored as ID references, never file paths (D1).
- Authoring language: English for directives and reference content; Spanish where content is institution-facing; never mix languages within one file (D7).
- Edit authority follows blast radius: project- and component-layer edits require a coordinator + PR; leaf edits require the node owner (D8).
- Never commit secrets, credentials, or internal URLs. No PII, ever.

## The 10 locked decisions

- **D1** — Node IDs are proposal codes (C#P#, INF#); dependency edges are ID references, never file paths.
- **D2** — A node is a folder: structured data (`node.yaml`, `directives.yaml`) + prose (`reference.md`).
- **D3** — Directives are keyed with `op` (`set`/`extend`/`suppress`) and `applies_to` tags; composition filters by node `kind`.
- **D4** — Composed output is generated (`.composed/` JSON + Markdown), rebuilt by CI, never hand-edited.
- **D5** — Cross-cutting rules live at the project layer (governance in C1P3, standards in C6P1).
- **D6** — Downstream product repos generate their AGENTS.md from the composed node; truth flows context → repo, never reverse.
- **D7** — English for directives and reference content; Spanish where institution-facing; no mixed-language files.
- **D8** — Edit authority by blast radius: project/component edits need coordinator + PR; leaf edits need the node owner.
- **D9** — The token meter is pinned to a target-model tokenizer and reported as an estimate on the worst-case (deepest) leaf of a branch.
- **D10** — The RAG interface is frozen (per-node `corpus/` manifest + branch-scoped query); embedding model and vector store are swappable behind it.

## Regenerating composed context

The `.composed/` files are built by the composer in `tools/composer/` — never hand-edit them (D4).

```
uv pip install -e "tools/composer[dev]"
python -m infotp_composer compose --all      # rebuild every node's .composed/<ID>.{json,md}
python -m infotp_composer compose C4P3        # rebuild a single node
python -m infotp_composer compose --check     # CI gate: fail if .composed/ is stale vs source
```

The composer walks each node's parent chain (project → component → deliverable), resolves directives by key with `set`/`extend`/`suppress`, filters them by the target node's `kind`, unions the reference corpus up the chain, and writes a JSON (for MCP/tools) and a Markdown (for humans) per node, plus a heuristic token estimate (D9). Run `compose --all` after any edit to a `node.yaml`, `directives.yaml`, or corpus, and commit the regenerated `.composed/` alongside your change.

## Retrieving reference context (RAG, D10)

Reference context is not inlined and not token-budgeted — it **accumulates** up
the tree and is **fetched on demand**, so it costs ~0 always-on tokens. Each
node lists its source documents in `<node>/corpus/manifest.yaml` (validated
against `schemas/corpus.schema.json`); the `infotp_rag` engine in `tools/rag/`
indexes them and answers **branch-scoped** queries — a query for a node returns
only chunks whose owning node is on that node's project→component→deliverable
chain, so sibling branches never leak into each other.

```
uv pip install -e tools/composer -e "tools/rag[dev]"   # rag depends on composer
python -m infotp_rag index --all                        # (re)build the .rag/ index
python -m infotp_rag query C1P1 "service alerts" -k 5 --json
```

The index (`.rag/`) is a derived build artifact and is gitignored — embeddings
are not byte-stable across backends, so the committed truth is the corpus files
plus their `manifest.yaml`. The embedding model and vector store are swappable
behind a frozen interface (D10): the default `hashing` embedder is deterministic
and offline (used by CI); the optional `[semantic]` extra adds a local
multilingual model for accurate search. Adding or removing a corpus file changes
a node's composed reference list, so run `compose --all` and commit the
regenerated `.composed/` alongside the corpus change.

## Two-hop reachability

Everything an agent needs should be reachable within two hops of this file: one hop to a node's `node.yaml`/`directives.yaml`/`reference.md`, or to `schemas/` for the format definitions, or to `.composed/<ID>.*` for the pre-built context of any node.
